responsibility-tree: adding responsibilities, projects and products

bin/responsibility-tree runs this protocol in the ClankOS container.
poslib's doc/pos-directory.txt defines the declarations it writes:
https://github.com/ClankaOperatingSystem/poslib


1. The tree

A garden is a tree. A responsibility is a branch: an area of life or
work that is tended and does not finish. It holds responsibilities,
projects and products. A project is a leaf: a finite piece of work
with an outcome. A product is a leaf too: a repository the garden
works on, under that repository's own rules.

A node's configuration declares what is directly beneath it, each as a
path. Where the path is, and what is at it, say what it is:

    no configuration                                     a product
    a configuration, where the node's projects belong    a project
    any other configuration                              a responsibility

A file or a directory where a responsibility's projects belong is a
project too, with no configuration and no entry. A path directly
beneath a node's methodologies path is a methodology, whatever is
there: a directory or a repository that supplies the node skills and
commands, as poslib's doc/pos-directory.txt section 6 and
doc/pos-methodology.txt have it. A responsibility may have
methodologies, as a project may.

A coding agent shows a session the skills of the directory it is
opened in and of each directory above it in the same repository. So a
project that is a directory of its responsibility's repository works
with the skills of its responsibility's methodologies, and a project
that is a repository of its own does not. Which a project is, is
chosen when the tree is laid out.

No folder name carries meaning, with one convention: a responsibility
keeps its one-file projects where its configuration says they belong,
which is projects/.


2. What each addition does

The command works on the garden in the working directory, which is a
responsibility. To add beneath one of its responsibilities, it is run
in that directory.

  - A responsibility NAME. The directory NAME is made, with
    .clanka/config.yml saying its projects belong in projects/ and
    naming the image this garden runs, and intray.org. Its path is
    added to this garden's children.
  - A project NAME. The file NAME.org is made where this garden's
    projects belong, with a title and a heading for its tasks. A
    garden whose configuration does not say where they belong is told
    so, and the project is not made. Making
    the file is the commitment, and nothing declares it: the file
    begins with a property drawer whose STATUS is COMMITTED, by which
    startup-prompt lists the project until it has a review scheduled,
    and whose OUTCOME is empty, to be written as one line.
  - A product PATH=REMOTE. An entry with that path and remote is
    added: to this garden's children, or, where a responsibility of
    this garden is on the way to PATH, to that responsibility's, since
    a node declares only what is directly beneath it. The repository
    is cloned afterwards, outside the container (section 5).

A name is one part of a path: letters, digits, dot, dash and
underscore, not beginning with a dot. Existing configuration and
content are kept, and an entry already made is kept. Nothing is committed.
Afterwards poslib updates the owning repository's managed archive
rules in Git's info/exclude, using each scope's own archive policy.
This includes newly created responsibilities, whose archives default
to uncommitted. Other ignore rules and already tracked files stay as
they are. What ClankOS installs is then brought up to date
(docs/refresh.txt), so that a responsibility or project just declared,
whose repository is there, has the commands and skills.

A project that needs more than one file is given a directory and a
configuration of its own. This command does not do that.


3. Asking

With options, it does what they say and asks nothing. At a terminal
with no option, and with --ask, it asks for responsibilities, then
projects, then products, each until an empty answer.


4. The report

Each thing written, declared or kept is printed on a line. Then
poslib's plan of the tree is read, and printed from it:

    finding   what is wrong in the tree: a declared directory that is
              missing, a configuration nothing declares, a node that
              does not say what it is
    to clone  a declared repository that is not there yet


5. Cloning

The container holds none of the user's Git credentials, so nothing is
cloned in it. bin/responsibility-tree, which starts the container,
clones afterwards with the git of the machine it runs on: each
repository the report gave as to clone, at its declared remote and
branch, from the root of the repository the garden is in. Each is
reported:

    cloned    PATH from REMOTE
    not cloned PATH from REMOTE    on standard error, after git's own
                                   message

A cloned repository can hold a configuration that declares more
repositories. So the container is asked again what is still to clone,
with "responsibility-tree --to-clone", which changes nothing and
prints a line for each: path, remote and branch, a tab between. This
goes on until a round clones nothing. A repository that could not be
cloned is tried once in a run, and again at the next.

With --no-clone, nothing is cloned and the report stands as it is.
initiate asks for the tree inside the container and clones nothing:
run bin/responsibility-tree afterwards.


6. Exit status

    0     done
    1     a name or a path was refused, or a repository was not
          cloned; the rest was done
    2     not a garden, or usage
    125   Docker failed to run the container
    126   the workspace is not visible in the container
    127   docker, or the command in the image, was not found
