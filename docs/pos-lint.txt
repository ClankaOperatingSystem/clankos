pos-lint: what is wrong in the Org files, and a methodology's checks

bin/pos-lint runs this protocol in the ClankOS container. The command
is poslib's pos-lint, at the commit the image was built with:
https://github.com/ClankaOperatingSystem/poslib


1. What is checked

The working directory is the root. The files are the corpus poslib's
doc/pos-directory.txt describes: every Org file under the root but
those in the directories the configuration excludes, and those of a
repository mounted within the tree, which that repository's own lint
reports.

Each file is checked for:

  - a done entry, DONE or CANCELLED, with an open entry beneath it,
    which the sweep would leave behind;
  - a heading that starts with a retired keyword, one not in poslib's
    sequence;
  - a #+TODO line, which would give the file a sequence of its own;
  - a copy of a task that dedupe has merged and not yet removed;
  - in an intray.org, an item under Unsorted that is not TODO: one
    that is NEXT, WAITING or SOMEDAY has been clarified and is to be
    placed, and a done one is to be retired;
  - a WAITING item that does not say who or what it waits on, in a
    DELEGATED_TO property or in its own text, or since when, in the
    record of its change to WAITING or a date in its own text;
  - no file-level ID, or an empty one: an ID in the property drawer
    before the first heading. A heading's ID or CUSTOM_ID names the
    heading, not the file.

A product's Org files are among those checked. In a file the root's
repository does not hold, a product's or another repository's of the
tree, a #+TODO line is not reported: the line is that file's own.
Nor is a missing file-level ID: the root lays no rule on such a file.

Then the whole tree, for:

  - a task heading written in more than one file, each copy naming
    the others;
  - a file-level ID that more than one file has, at each file the
    root's repository holds, naming the others;
  - an entry of a node's skills-lock.json of a skill that its declared
    source's entry does not name (poslib's doc/pos-directory.txt,
    section 6), at the entry's line, as "lock-undeclared: NAME: ...".
    An entry of a source no configuration declares is wild-caught, and
    is not reported.

Then each methodology a project of the tree uses (poslib's
doc/pos-methodology.txt): each executable scripts/check-* of each of
its skills is run in the project, and what it prints is reported among
the findings. The skills are those in a mounted methodology's skills/,
and those install wrote in the project's .agents/skills/ from a
declared source.


2. Findings

One line each, sorted by file and then line:

    FILE:LINE: MESSAGE

FILE is relative to the root. A check's finding is as the check printed
it, FILE made relative to the root; a line a check printed that is not
of that form is a finding at the project; a check that exited 2 is a
finding at its skill, with what it printed on stderr. A declaration,
methodology.yaml, that the lint cannot read, or that names checks in
the methodology's bin/, which are not run, is a finding at the
methodology.

Nothing is changed, and nothing is written to the root.


3. In the container

The command runs in the working directory's repository, mounted at its
own path. The root's pos-config.el is loaded if there is one. A
methodology's check runs with the project as its working directory, as
a program of the image: a check that needs what the image lacks exits
2 and is reported so.

Exit: 0 nothing to report, 1 findings, 2 usage, 255 an Emacs error, its
message on stderr.
