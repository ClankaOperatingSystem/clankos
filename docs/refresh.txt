refresh: keeping what ClankOS installs in a repository current

refresh runs this protocol in the ClankOS container. poslib's
doc/pos-directory.txt, section 6, defines what is installed, and the
operation is its "install":
https://github.com/ClankaOperatingSystem/poslib


1. What is installed

The image holds a source: the scripts that start its commands, and its
skills, with a version that changes when any of them does, and the
repository and the commit the image was built from. In a
repository that has a configuration at its root, a garden's or a
mounted responsibility's or project's, the source is installed:

    .clanka/auto/    a copy of the source. It is ClankOS's alone and is
                     replaced whole when the image's version is
                     another. What anyone else writes in it is lost.
                     In a repository whose configuration is in
                     .clankos/ or .pos/, it is .clankos/auto/ or
                     .pos/auto/
    bin/NAME         where the configuration says "bin: bin", a link to
                     each command in auto/bin/
    .codex/rules/clankos.rules
                     Codex's approvals: a rule for each way the
                     repository has of starting a command, so that
                     Codex runs ClankOS's commands without asking

All of it is untracked, its paths in Git's info/exclude. So a new
clone has none of it until refresh or initiate has run there. A
command of a slot's name, capture, start-up or wrap-up, is linked only
where the repository holds none of its own (section 3).

The image's skills are not linked. install installs them, as a source
of the repository's skills-lock.json: from the repository the image
was built from, at its commit ("clankos-run help install"). Each
skill's scripts/clankos starts the configured runtime directly.

A repository with no configuration is a product. Nothing is written in
it.

Codex asks before a command no rule of its allows. The rules file
holds a prefix_rule for each link to a command and each installed
skill's scripts/clankos, in the repository and in each configured
repository mounted beneath it, each in three spellings: relative to
the repository, with ./ before it, and absolute, which holds from any
directory. The command's arguments are not matched, so a rule allows
every use of the command. Codex reads the file when it is started in
the repository and the repository is trusted there; its documentation
says how a project is trusted and how its rules are read. The file is
written whether or not Codex is used, and replaced whole when what it
lists changes. Where the repository tracks a file of that name, it is
left as it is and reported as a taken name (section 3).


2. When it runs

Ordinary commands do not run refresh. Invoke "clankos-run refresh" to
rebuild wrappers and approvals explicitly. Initiate also runs refresh after
writing configuration. Use apply-v1 to apply configured skill sources;
migrate path methodologies to source declarations (docs/apply-v1.txt).

The explicit --if-changed option can reuse the last refresh result when
its inputs have not changed. It is not invoked by ordinary commands.

It uses no network and clones nothing. It also brings to the same
state each configured repository mounted beneath the one it runs in.


3. A name that is taken

Where a link is to be made and something else has the name, a file, a
directory or another link, refresh leaves it as it is and says so on
stderr, with whether Git tracks it and the commit that added it:

    clankos: name-taken bin/pos-capture (tracked, added in 1a2b3c4)

It says so before every command, until the name is free: a coding
agent may take what has the name for ClankOS's skill. The other links
are made. A garden made by an earlier image has copies of the scripts
in bin/, which are reported in this way; removing them lets the links
be made.

A slot's name is the exception. A command in bin/ that the repository
holds under capture, start-up or wrap-up, tracked or not, is the
repository's own filling of that slot (poslib's doc/pos-slots.txt):
refresh makes no link there and says nothing. So is a skill of a
slot's name in .agents/skills/ that install did not put there from
the image: the image's skill of that name is not installed in that
repository.


4. A node's methodologies

The methodologies of a node, a project or a responsibility, each
declared directly beneath its methodologies path, supply skills and
commands the same way, by links to them where they lie, with nothing
copied: poslib's doc/pos-directory.txt, section 6. The links are made
in the node, at its repository's root beside the image's links when it
is a repository, and in its own directory when it is a directory of
one. A
methodology whose skill is not named with the methodology's name and
a hyphen is left out and said so on stderr, until it is renamed:

    clankos: methodology-refused projects/p/methodologies/hello (a skill not named hello-NAME: greet)


5. The lock file

A node that declares methodologies as sources, and a repository's
root, which has the image's skills, has the skills in .agents/skills/
and a record of them in skills-lock.json, which "clankos-run install"
writes ("clankos-run help install"). refresh compares the
configuration, the image's skills counted as declared, with
skills-lock.json, and each entry with its skill's directory, with no
network, in each node of the repository it runs in, and says where
they differ:

    clankos: lock-differs skills-lock.json (https://example.org/team/pr-gnome.git at v1.3.0: not installed)
    clankos: lock-differs skills-lock.json (pr-gnome-write: changed since it was installed)
    clankos: lock-undeclared skills-lock.json (hello-other: not among the skills of https://example.org/team/hello.git)

lock-differs is a source, a skill or a ref the configuration declares
that skills-lock.json does not hold, or an installed skill whose
directory is gone or no longer has the hash its entry records;
lock-undeclared is an entry of a skill that a declared source's entry
does not name. Running install brings the two into line. A new image
is at another commit, so after the image changes refresh says
lock-differs for its skills until install has run.

A skill someone installed with the skills CLI from a source the
configuration does not declare is wild-caught. It is no fault: refresh
names it, and does not exit 1 for it, and install leaves it as it is.

    clankos: wild-caught skills-lock.json (grill-me: from someone/skills, which is not declared)


6. Where links cannot be made

On a file system that refuses a symbolic link, refresh says so, and
the commands are not linked. The command it ran before goes on.


7. Exit status

    0     done, or not in a Git repository
    1     a name is taken, or a skills-lock.json differs from its
          configuration
    2     usage, or poslib refused
    3     a link cannot be made
    125   Docker failed to run the container
    126   the workspace is not visible in the container
    127   docker, or the command in the image, was not found

Run before another command, its status is not that command's.
