startup-prompt: what a session opens with

bin/startup-prompt runs this protocol in the ClankOS container. The
command is poslib's pos-startup, at the commit the image was built
with: https://github.com/ClankaOperatingSystem/poslib


1. What it is for

A session opens by choosing what to do. The choice needs to know what
is already waiting: what is next, what has a date, what is due, what is
to be reviewed, what is captured and not yet placed. Finding that by
opening each Org file is slow and misses things.

startup-prompt prints four prompts, for the choice, and then views of
the saved Org files, for what is waiting. It chooses nothing and writes
nothing to the root. It does bring the index org-roam keeps of the
root's Org files up to date, in the cache directory clankos-run
mounts, so that every session leaves it current for the commands that
read it, pos-dedupe among them.


2. The prompts

    Purpose         What are we here to do in this session?
    Circumstances   What time, attention, energy, and fixed commitments
                    constrain the choice?
    Choice          Which established work, new concern, or
                    clarification should begin?
    Trust           Treat the views below as a bounded view of saved
                    files, not a complete review.

They are the same on every run.


3. What is read

The working directory is the root. The files read are the corpus
poslib's doc/pos-directory.txt describes: every Org file under the
root except those in the directories the configuration excludes,
which by default are archives, attic, node_modules and names
beginning with an underscore or a full stop, at any depth; hidden
files, lock files and symbolic links are not read.

The walk follows the declarations. From a directory with a
configuration it enters the ordinary directories and each child the
configuration declares. A declared child with a configuration of its
own is read as that configuration says. A declared child with none is
a product: its Org files are read as the product's, with the default
exclusions. A directory with a configuration that nothing declares is
not entered, and is named after the count of files, as "Not read".

A file belongs to a scope: the deepest project, responsibility or
product on its path. A file under none belongs to the root.

    responsibility   a directory beneath the root whose configuration
                     says where its projects belong, which is what
                     responsibility-tree makes
    project          what lies where that configuration says the
                     projects belong: NAME.org, or the directory NAME
    product          a declared child with no configuration: a
                     repository the garden works on. Its files are
                     read and never written, and each keeps the
                     keywords of its own #+TODO line

A directory's name alone makes it none of these. The root is a
responsibility, and is not listed as one. A configuration that is
refused is named after the count of files, as "Not read", and nothing
beneath it is read.

A methodology a project uses (poslib's doc/pos-methodology.txt) is not
read: its own files are not the project's. Where it declares kinds of
canon it maintains in the project, decision records in Markdown say,
the report lists them after the count of files, one line per kind:

    Canon of other kinds, not read:
      PROJECT  METHODOLOGY  KIND  AT  start at ENTRANCE

so that a session knows what the views do not cover and where to start
reading it. Nothing of those kinds is in any view.

The keywords are poslib's one sequence: TODO, NEXT, WAITING and SOMEDAY
are open; DONE and CANCELLED are done. A done item is in no view.

After the prompts, "Files read: N" says how many files were read.


4. The views

Each view is a title, then one line for each item: the item's scope,
then the item. A view of more than one list has a title for each. A
list with no item says "(none)".

    next                 Every item whose keyword is NEXT, in three
                         lists: projects', responsibilities', then
                         the root's. A product's, and those of a
                         directory whose configuration does not yet
                         say what it is, are each in a further list,
                         printed only when it has an item.
    waiting              Every item whose keyword is WAITING.
    someday              Every item whose keyword is SOMEDAY: what
                         is kept and not committed to, for a review
                         to read.
    scheduled            Items scheduled in the next 14 days, under
                         their dates, and those scheduled earlier and
                         still open, as late. Reviews and deadlines
                         are left to their own views.
    deadlines            Every open deadline, once, with the days
                         until it or since it. None is left out for
                         being far off.
    reviews              Review items late or scheduled in the next 7
                         days: projects', then responsibilities', then
                         the root's, which review the whole tree.
    reviews-to-schedule  Active projects, then responsibilities, then
                         the root, named ".", that no review covers.
                         A path a review names that is no scope's is
                         in a fourth list, printed only when there is
                         one.
    stuck                Projects whose STATUS is WIP and none of
                         whose files has a NEXT or WAITING item.
    projects             Each active project, three lines: its path,
                         STATUS and the date of its next review; its
                         first NEXT or WAITING item; and its outcome,
                         which is the OUTCOME property of its file,
                         with any OUTCOME+ lines joined to it. What
                         it lacks is a dash.
    intray               Every open item under the heading "Unsorted"
                         in a file named intray.org, the root's and
                         each scope's: what pos-capture has added and
                         nobody has yet placed.
    finished             Every done item whose CLOSED date is today
                         or in the 7 days before it, with that date.
                         A done item with no CLOSED date is not
                         listed.
    all                  Every open item.

A review item is an open heading tagged :review: with a scheduled
date, in a file of the scope it reviews; which file is the person's
choice ("clankos-run help review"). It covers that scope. It also
covers each scope its COVERS property names, by paths from the
directory of its own file, apart by spaces, a space within a path
written %20:

    * TODO Review the shop :review:
    SCHEDULED: <2030-03-04 Mon +1w>
    :PROPERTIES:
    :COVERS:   shop projects/ledger
    :END:

In work/index.org that heading covers work, work/shop and
work/projects/ledger. This is for a scope whose review is kept in the
scope above it, as when the scope is a repository other people share.
Nothing is inherited: a review covers no scope it does not name.

An active project is one
whose project file has, before its first heading, a STATUS property of
COMMITTED or WIP, in a property drawer that begins the file:

    :PROPERTIES:
    :STATUS: COMMITTED
    :END:

responsibility-tree gives a new project that drawer.

The label of a line is its file's directory under the root, without
the segments named projects, and with the file's name added unless it
is project.org: projects/alpha/project.org is "alpha", and
projects/alpha/notes.org is "alpha/notes". A project.org at the root
itself is ".".

With no --view, every view but someday, projects, finished and all is
printed, in the order above.
"--view NAME", repeated, prints the prompts and those views only.
"--weekly" stands for the views of a weekly review, in the order the
review reads them: intray, next, waiting, scheduled, deadlines,
reviews, stuck, reviews-to-schedule, someday, finished.


5. The views as JSON

"--json" prints one line of JSON in place of the text, for a program
to read:

    files_read   the count of files read
    not_read     path and reason for each configuration not read
    views        each view named, with what it lists, in the order of
                 its text

In a view of items each element has scope, scope_kind, file, line, id,
state, title, tags, scheduled, deadline, closed, properties and body.
The dates are as written; what an item lacks is null. In
reviews-to-schedule, stuck and projects, which list scopes, each has
scope, scope_kind and status; in projects, review, next and outcome
too. A view named twice is given once.


6. Settings

The root's pos-config.el, if it has one, is loaded. It can set:

    pos-startup-scheduled-days             14
    pos-startup-review-days                7
    pos-startup-finished-days              7
    pos-startup-review-tag                 "review"
    pos-startup-review-covers-property     "COVERS"
    pos-startup-active-statuses            ("COMMITTED" "WIP")
    pos-startup-stuck-statuses             ("WIP")
    pos-startup-next-action-states         ("NEXT" "WAITING")

Which directories are read is not a setting here: the configuration
declares it, under exclude.


7. In the container

bin/startup-prompt gives its arguments to bin/clankos-run. The files
are the host's, at their own paths. The container is given the host's
time zone, so that "today", "late" and "due" are counted from the same
day as on the host. pos-config.el is Lisp, and is run in the container.

The report is on stdout. Emacs's own messages are on stderr.


8. Exit status

    0     printed
    2     usage
    255   an Emacs error; the message is on stderr
    125   Docker failed to run the container
    126   the workspace is not visible in the container
    127   docker, or the command in the image, was not found
