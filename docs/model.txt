model: the things ClankOS installs, and how they fit

"clankos-run help model" prints this document. It names each thing,
says what contains or points at what, and lists the requirements on
each that the tests check. "clankos-run help words" gives each word one
line and says where it is defined.


1. The things

    tree             a root, the responsibilities beneath it, and each
                     one's projects and products. A node is a
                     responsibility or a project with a configuration
                     of its own. A mount is a node or a product that is
                     a repository of its own.
    configuration    config.yaml or config.yml in a node's .clanka,
                     .clankos or .pos: the image it runs, and the
                     sources it declares under methodologies.
    source           a Git repository, declared at a ref, of one kind:
                     methodology, whose skills are named with the
                     repository's name and a hyphen and may carry
                     checks; or skills-repository, whose skills are
                     taken as their author named them.
    skill            a folder holding SKILL.md, with references/ for
                     what the agent reads and scripts/ for what it
                     runs. The format is agentskills.io's.
    check            scripts/check-NAME in a skill of a methodology,
                     executable; the lint runs it and reports its
                     findings as its own.
    lock             skills-lock.json beside .agents/skills/: each
                     skill installed, its source and the ref it was
                     installed at.
    image            the ClankOS container image: Emacs, poslib and
                     the commands, and method zero, the image's own
                     skills, named clankos-NAME, with the slots it
                     fills.
    harness          the program the coding agent runs in, which reads
                     .agents/skills/ and offers the agent what it
                     finds there.
    gnome            a methodology that also holds a doctrine,
                     policies and cases, which a bugflow server reads.
                     To this side it is a methodology and nothing
                     more; bugflow's docs/architecture.md models the
                     rest.


2. How they fit

    tree
     └─ node ──────── configuration
                        ├─ image ──────── method zero: commands and skills
                        └─ source (at a ref) ──┬─ methodology ── skill ── check
                                               └─ skills-repository ── skill
                                         │
                      install copies each source's skills, and the
                      image's, into .agents/skills/ and records them
                      in the lock.
                                         │
                      lint runs each methodology's checks;
                      a harness offers every skill to the agent.

    A mount has a configuration, an install and a lock of its own. A
    command run in it works on it and never looks upward.

    A gnome crosses to bugflow at one point: the ref a node declares
    it at is the commit a binding pins it at. Nothing else is shared.


3. The requirements, and what holds each

    Each requirement is the name of a check in test/model/, one script
    for each group, and scripts/render-model writes this section from
    them. A requirement poslib holds runs poslib's test in the image.
    One marked "not tested" names what holds it instead.

    The tree, test/model/tree.sh
      - A tree is a root, the responsibilities beneath it, and each
        one's projects and products.
      - A node is a responsibility or a project that has a configuration
        of its own.
      - A mount is a node or a product that is a repository of its own.
      - A walk of the tree reads a mount's files.
      - No command run above a mount writes a mount's files.
      - A mount has a configuration, an install and a lock of its own.
      - A command run in a mount works on that mount and never looks
        upward.

    The configuration, test/model/configuration.sh
      - A node's configuration is one file, config.yaml or config.yml,
        in a directory of the node named .clanka, .clankos or .pos.
      - The configuration names the image the node runs.
      - The configuration declares the node's sources under
        methodologies.

    A source, test/model/source.sh
      - A source is declared by a Git URL.
      - A source is declared at a tag or at a full commit.
      - A source is of one kind: methodology or skills-repository.
      - A methodology's skills are named with the repository's name and
        a hyphen.
      - A skills-repository's skills keep the names their author gave
        them.
      - No source supplies a skill whose name begins with clankos-.

    A skill, test/model/skill.sh
      - A skill is a folder that holds SKILL.md.
      - A skill's references/ holds what the agent reads. Not tested:
        held by agentskills.io's format.
      - A skill's scripts/ holds what the agent runs. Not tested: held
        by agentskills.io's format.
      - A skill folder follows agentskills.io's format. Not tested: held
        by the skills CLI.
      - ClankOS reads only the skill folder's name. Not tested: nothing
        holds it.

    A check, test/model/check.sh
      - A check is a file scripts/check-NAME in a skill of a
        methodology.
      - A check is executable.
      - The lint runs each check of each methodology's skills.
      - The lint reports a check's findings as its own.

    Install and the lock, test/model/lock.sh
      - Install copies each source's skills into .agents/skills/.
      - The lock is the file skills-lock.json beside .agents/skills/.
      - The lock names each skill installed, its source and the ref it
        was installed at.
      - Refresh reports a lock that differs from the configuration.
      - A wild-caught skill is one whose lock entry names a source the
        configuration does not declare.
      - Refresh names each wild-caught skill and exits 0.
      - The lint reports a lock entry of a skill that its declared
        source does not name.
      - The lint does not report a wild-caught skill.

    The image and method zero, test/model/method-zero.sh
      - The image holds Emacs, poslib, the commands and method zero.
      - Method zero's skills are named clankos-NAME, apart from the
        slots it fills.
      - The image installs method zero at the commit the image was built
        from.
      - Method zero's skills are installed in .agents/skills/ as
        folders.
      - No configuration names method zero's skills.
      - A declared source's skill of a slot's name is installed in place
        of method zero's.

    The slots, test/model/slots.sh
      - A slot is a skill a repository may fill with a skill of its own:
        capture, start-up or wrap-up.
      - poslib's doc/pos-slots.txt gives each slot's signature. Not
        tested: held by poslib's doc/pos-slots.txt.
      - Install leaves a slot that the garden fills alone.

    The harness, test/model/harness.sh
      - A harness offers the agent every skill in .agents/skills/. Also
        held by the harness.

    A gnome, test/model/gnome.sh
      - To ClankOS, a gnome is a methodology and nothing more. Not
        tested: nothing holds it.
      - ClankOS never reads a gnome's doctrine, policies or cases. Not
        tested: nothing holds it.
      - A gnome's own tests keep the copies in a skill's references/
        equal to their originals. Not tested: held by each gnome's own
        tests.
